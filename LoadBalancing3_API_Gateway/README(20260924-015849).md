# Spring Cloud Load Balancing with Eureka and API Gateway

This project demonstrates **service discovery and client-side load
balancing** using Spring Boot, Netflix Eureka, Spring Cloud Gateway, and
Spring Cloud LoadBalancer.

The same Payment Service is started as three separate instances. Clients
send requests only to the API Gateway, and the Gateway uses service
discovery and load balancing to route requests across the available
Payment Service instances.

## Architecture

``` text
                         Eureka :8761
                       Service Registry
                              |
                +-------------+-------------+
                |             |             |
                v             v             v
         paymentService paymentService paymentService
             :8081          :8082          :8083

Client
  |
  v
API Gateway :8080
  |
  v
Spring Cloud LoadBalancer
  |
  +-------------+-------------+
  |             |             |
  v             v             v
:8081         :8082         :8083
```

## Projects

The example consists of three Spring Boot projects:

1.  **Discovery Server**
    -   Runs Netflix Eureka.
    -   Keeps track of registered service instances.
    -   Runs on port `8761`.
2.  **Payment Service**
    -   Contains the Payment REST API.
    -   The same application is launched three times.
    -   Instances run on ports `8081`, `8082`, and `8083`.
    -   All instances register with Eureka using the service name
        `paymentService`.
3.  **API Gateway**
    -   Receives requests from clients.
    -   Runs on port `8080`.
    -   Uses `lb://paymentService` to locate and load-balance requests
        across Payment Service instances.

## Request Flow

When a client calls:

``` text
/api/payments/test
```

the request follows this flow:

``` text
Client
   |
   v
API Gateway :8080
   |
   | Path matches /api/payments/**
   v
lb://paymentService
   |
   v
Spring Cloud LoadBalancer
   |
   | Gets available instances from Eureka
   v
+----------+----------+----------+
|          |          |          |
v          v          v
8081       8082       8083
```

Eureka performs **service discovery**. It tells the Gateway which
instances of `paymentService` are registered and available.

Spring Cloud LoadBalancer then chooses an instance. With the default
round-robin load balancer, requests are distributed across the available
service instances. The exact first instance/order should not be relied
upon.

For example:

``` text
Request 1 -> 8081
Request 2 -> 8082
Request 3 -> 8083
Request 4 -> 8081
...
```

## Discovery Server Configuration

`application.properties`:

``` properties
spring.application.name=LoadBalancing1_discoveryServer
server.port=8761

eureka.client.register-with-eureka=false
eureka.client.fetch-registry=false
```

The Discovery Server itself does not need to register as a client
because it is the Eureka server.

## Payment Service Configuration

`application.properties`:

``` properties
spring.application.name=paymentService

server.port=${PORT:8081}

eureka.client.service-url.defaultZone=http://localhost:8761/eureka/

eureka.instance.instance-id=${spring.application.name}:${server.port}
```

`PORT` allows the same application to be started multiple times on
different ports.

The three instances should run as:

``` text
paymentService:8081
paymentService:8082
paymentService:8083
```

## Payment Controller

``` java
package com.example.controller;

import org.springframework.beans.factory.annotation.Value;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequestMapping("/api/payments")
public class PaymentController {

    @Value("${server.port}")
    private String port;

    @GetMapping("/test")
    public String test() {
        return "Payment processed by server running on port: " + port;
    }
}
```

The port is included in the response so it is easy to see which Payment
Service instance handled each request.

Example responses:

``` text
Payment processed by server running on port: 8081
Payment processed by server running on port: 8082
Payment processed by server running on port: 8083
```

## API Gateway Configuration

`application.properties`:

``` properties
spring.application.name=LoadBalancing3_API_Gateway

server.port=8080

eureka.client.service-url.defaultZone=http://localhost:8761/eureka/

spring.cloud.gateway.server.webflux.routes[0].id=payment-service
spring.cloud.gateway.server.webflux.routes[0].uri=lb://paymentService
spring.cloud.gateway.server.webflux.routes[0].predicates[0]=Path=/api/payments/**
```

The most important setting is:

``` properties
spring.cloud.gateway.server.webflux.routes[0].uri=lb://paymentService
```

`paymentService` is the service ID registered with Eureka.

The `lb://` prefix tells Spring Cloud Gateway to use Spring Cloud
LoadBalancer instead of routing to one fixed host and port.

## How Load Balancing Works

The three components have different responsibilities:

``` text
Eureka
"What service instances are available?"
              |
              v
Spring Cloud LoadBalancer
"Which available instance should handle this request?"
              |
              v
API Gateway
"Forward the request to the selected instance."
```

Suppose Eureka knows about:

``` text
paymentService
    |
    +-- 8081
    +-- 8082
    +-- 8083
```

When requests arrive at the Gateway, Spring Cloud LoadBalancer selects
from these available instances.

Conceptually:

``` text
                Gateway
                   |
                   v
          RoundRobinLoadBalancer
                   |
          +--------+--------+
          |        |        |
          v        v        v
        8081     8082     8083
```

This is similar to a basic round-robin algorithm:

``` java
String nextServer = servers.get(currentIndex);
currentIndex = (currentIndex + 1) % servers.size();
```

Spring Cloud uses `ServiceInstance` objects discovered through Eureka
rather than a manually maintained list of server ports.

## What Happens if an Instance Goes Down?

Initially Eureka may have:

``` text
8081 -> UP
8082 -> UP
8083 -> UP
```

If one instance stops and Eureka eventually determines that it is
unavailable, the usable set becomes:

``` text
8081 -> UP
8083 -> UP
```

The LoadBalancer can then choose from the remaining available instances.

Eureka uses heartbeats, leases, and registry caching, so removal of a
stopped instance is not necessarily instantaneous.

## Starting the Applications

Start the applications in this order:

``` text
1. Eureka Discovery Server       -> 8761
2. Payment Service instance      -> 8081
3. Payment Service instance      -> 8082
4. Payment Service instance      -> 8083
5. API Gateway                   -> 8080
```

After starting them, verify in the Eureka dashboard that
`PAYMENTSERVICE` has three `UP` instances.

Then send repeated requests through the API Gateway using:

``` text
/api/payments/test
```

The returned port number demonstrates which Payment Service instance
processed each request.

## Common Errors Encountered

### 404 Not Found

A `404` can occur when the Gateway route is not loaded or the incoming
path does not match the configured route.

For the Spring Cloud Gateway version used by this project, the route
configuration uses:

``` properties
spring.cloud.gateway.server.webflux.routes[0]...
```

### 500 - Invalid Host

An earlier service name contained an underscore:

``` text
LoadBalancing2_paymentService
```

Using that directly in an `lb://` URI caused an invalid-host error.

The service name was simplified to:

``` text
paymentService
```

Therefore the Gateway uses:

``` properties
spring.cloud.gateway.server.webflux.routes[0].uri=lb://paymentService
```

### 503 Service Unavailable

A `503` with a message such as:

``` text
No servers available for service: paymentService
```

means the Gateway route and LoadBalancer are working, but no matching
service instance can currently be discovered.

In this project, this happened because the Payment Service processes
were still registered in Eureka under their old application name.

After changing:

``` properties
spring.application.name=paymentService
```

all Payment Service instances had to be completely restarted so they
could register with Eureka under the new name.

## Key Concepts

**Service Discovery:** Eureka maintains information about available
service instances.

**API Gateway:** Provides a single entry point and routes requests based
on configured predicates.

**Load Balancing:** Spring Cloud LoadBalancer selects an available
service instance instead of sending every request to one fixed instance.

**Round Robin:** Requests are distributed among available instances in
rotation rather than always selecting the same server.

**Horizontal Scaling:** Multiple instances of the same application can
run simultaneously, allowing traffic to be distributed among them.

The core flow of this project is:

``` text
Client
   |
   v
API Gateway
   |
   | lb://paymentService
   v
Spring Cloud LoadBalancer
   |
   | Service instances obtained through Eureka
   v
+----------+----------+----------+
|          |          |          |
8081       8082       8083
```

The main idea to remember is:

> **Eureka discovers the Payment Service instances, Spring Cloud
> LoadBalancer chooses an available instance, and API Gateway forwards
> the incoming request to that chosen instance.**
